## Finding 1 — Nightly coverage gate is structurally guaranteed to fail. Confidence 90. [BOTH]

**Problem.** Each CI job runs only one test group, but `check_coverage.jl` measures coverage of all of `src/` and demands 90%. `CI.yml` sets `EREBUS_TEST_GROUP: unit`; `nightly.yml` sets `EREBUS_TEST_GROUP: integration`. Nightly runs only 4 integration files, then asserts 90% coverage of the whole `src/` tree. No job ever measures full-suite coverage.

**Risk.** Nightly fails every night because integration-only tests cannot cover 90% of `src/`. The fast CI job also under-counts: any `src/` line reached only by an integration test is not covered, so the 90% floor is measured against a partial suite and can fail for reasons unrelated to the change under test. This couples the coverage gate to the test split; the two fight each other.

**Fix.** Do not run `check_coverage.jl` in the split jobs. Measure coverage once, in a dedicated job that runs `EREBUS_TEST_GROUP=all`. Or drop the per-job floor and upload coverage to a service that merges group results.

## Finding 2 — `check_coverage.jl` imports an undeclared dependency and will fail on a clean runner. Confidence 85. [ON-DISK; MATERIAL differs]

**Problem.** On disk, `check_coverage.jl` starts with `using Coverage`, but `Coverage` is not in `[deps]` or `[extras]`; the test target is `test = ["Test", "MPI"]`. CI runs the step as `run: julia tools/check_coverage.jl` with no `--project`, so it uses the global environment, where `Coverage` is not installed. `using Coverage` throws `ArgumentError: Package Coverage not found`.

**Evidence.** `Project.toml` lines 64-69 show no `Coverage`. The MATERIAL version had `Pkg.add("Coverage")`, which masked the missing dependency (at the cost of a slow, non-reproducible global mutation on every run). The RIP "fix" removed `Pkg.add` but did not declare the dependency, so it converted a slow step into a broken step.

**Fix.** Add `Coverage` to `[extras]` and to a `coverage` target, then run the script with that project active. Or install it explicitly in the workflow step. Do not rely on `Pkg.add` at script runtime.

## Finding 3 — The new bare-positivity rule contradicts the project's own documented rigor standard. Confidence 90. [BOTH]

**Problem.** The new `weak_assert` branch flags `@test x > 0`, `@test x >= 0`, `@test x < 0`, `@test x <= 0`. But `erebus-tests.md` section 4 makes the sign guard `@test val > 0.0` a required class of the 3-class discrimination guard, and the canonical example at line 126 contains the exact line `@test h_rad > 0.0`.

**Evidence (executed).** I ran the on-disk linter:
```
`@test h_rad > 0.0`  -> [:weak_assert]
`@test val < 0.0`    -> [:weak_assert]
`@test x >= 0`       -> [:weak_assert]
```
The linter now flags the exact pattern the rules mandate. The baseline is a one-way ratchet, so a new, correctly written 3-class test raises `weak_assert` above baseline and fails CI.

**Risk.** Following the documented standard breaks the build. Authors will drop sign guards to satisfy the linter, which removes the class-2 discrimination the rules exist to enforce. The tool defeats its own goal.

**Fix.** Do not flag a positivity assertion when it sits in a testset that also contains an `isapprox`/analytical pin (that is the 3-class context the rules allow). At minimum, reconcile the rule with `erebus-tests.md` and update the canonical example, so the doc and the linter agree.

## Finding 4 — Committed baseline keys do not match the counter's key format. Confidence 80. [MATERIAL; fixed on-disk]

**Problem.** The MATERIAL baseline uses global keys (`"float_equality": 32`, `"weak_assert": 377`), but `count_by_rule` emits per-file keys (`"test_physics.jl:weak_assert"`). In `--check`, every per-file key resolves to `get(baseline, key, 0) == 0`, so every file with any violation reads as a regression and CI always fails.

**Evidence.** On-disk `count_by_rule` (line 300-308) builds `string(basename, ":", rule)`. The MATERIAL baseline has no `:` in its keys. The on-disk baseline was regenerated to per-file keys, which is why this is already fixed.

**Fix.** None needed on disk. Flag: the baseline format is implicit and undocumented; a stale regeneration will silently reintroduce this. Add a format check that asserts every baseline key contains a `:`.

## Finding 5 — Per-file baseline ratchet is fragile to file renames and basename collisions. Confidence 82. [ON-DISK]

**Problem.** The ratchet keys on `basename(file):rule`. Rename `test_physics.jl` and its debt resets to 0 while its current count stays at 30, so CI fails until someone regenerates the baseline. Two test files with the same basename in different directories collide into one count.

**Risk.** Routine test refactors (rename a file, split a file, move violations between files) break the gate for reasons unrelated to test quality. The failure message points at "regression" when the real cause is a rename.

**Fix.** Key on the path relative to the test root, not the basename. Document that a rename requires a baseline regeneration, or key the ratchet on total-per-rule with a separate per-file report.

## Finding 6 — `is_suspected_float_var` swings between overbroad and unmaintainable. Confidence 85. [BOTH, different failure each side]

**Problem (MATERIAL).** The heuristic matches any symbol containing `zero`, `heat`, `temp`, `press`, `mass`, `dens`, `vol`, `flux`, `energy`, `frac`, `time`, or ending in `val`, plus any `:ref`. So `@test n_time == 5`, `@test mass_index == 3`, and `@test arr[i] == arr[j]` (both refs) are flagged as float-equality even for integers and booleans. The guard `!isa(arg, Integer)` does not help: the args are `Symbol`/`Expr` nodes, not literal `Integer` constants. The result is mass false positives that inflate the baseline and destroy trust in the linter.

**Problem (ON-DISK).** The RIP fix narrowed the heuristic to two hardcoded names:
```julia
return s == "v_zero" || s == "heat_solid_off"
```
**Evidence (executed).** `is_suspected_float_var(:v_zero) -> true`, `is_suspected_float_var(:temperature) -> false`, `is_suspected_float_var(arr[i]) -> false`. A generic AST linter now special-cases two specific test-variable names. It catches nothing general and rots the moment those variables are renamed or a third float variable appears.

**Fix.** Drop name-based guessing. Detect float equality structurally: flag `==` only when an operand is a float literal or a call to a known float-returning function; leave variable-vs-variable equality to reviewers. If you must catch specific variables, that belongs in a per-file allow/deny list, not baked into the linter source.

## Finding 7 — Manual dual test lists couple file existence to CI, and the MATERIAL version silently skips new tests. Confidence 78. [BOTH]

**Problem.** `runtests.jl` hardcodes `unit_tests` and `integration_tests` by filename. In the MATERIAL version a new test file that is in neither list is simply never run: `files_to_run` never includes it. The suite passes while the new test never executes, which is false confidence, the exact failure the rules doc warns against.

**Evidence.** MATERIAL `runtests.jl` has no completeness check. The on-disk version adds one (lines 72-78): it errors if any `.jl` file is not listed. That closes the silent-skip hole but now makes every new test file a hard CI failure until it is manually assigned to a group, and it maintains a third hardcoded exclusion list (`test_helpers.jl`, `test_constants.jl`, `mpi_worker_tests.jl`).

**Fix.** Derive the file list from disk. Tag group membership with a naming convention (`test_integration_*.jl`) or a small manifest, and glob the rest into `unit`. Then a new file runs by default and cannot be silently skipped.

## Finding 8 — Single `@test_throws` testsets now fail min_asserts, which blocks a legitimate error-contract pattern. Confidence 75. [ON-DISK]

**Problem.** The min_asserts rule flags any leaf testset with fewer than 2 assertions. A testset that holds a single `@test_throws` (a pure error-contract test, which the rules explicitly endorse in section 3.2) is flagged.

**Evidence (executed).**
```
@testset "e" begin @test_throws DomainError f(-1.0) end
  -> [(:min_asserts, "Testset contains fewer than 2 assertions ...")]
```
**Risk.** Authors merge unrelated error-contract tests into one testset just to reach 2, which reduces test isolation and produces worse failure messages.

**Fix.** Exempt a leaf testset whose only assertion is `@test_throws`, or count the error contract plus its companion as the intended pair and document the exemption.

## Finding 9 — `min_asserts` in MATERIAL flags parent testsets that own sub-testsets. Confidence 76. [MATERIAL; fixed on-disk]

**Problem.** MATERIAL used `if assert_count == 1 || (!has_sub_testsets && assert_count == 0)`. The `assert_count == 1` branch has no `!has_sub_testsets` guard, so a parent testset with one setup assertion plus several sub-testsets is flagged. On-disk fixed this to `(assert_count == 1 && !has_sub_testsets) || ...`. No action needed on disk; noted so you do not re-report it.

## Finding 10 — `timeout-minutes: 10` lands in the same change that enables coverage. Confidence 72. [BOTH]

**Problem.** Coverage instrumentation slows the Julia test suite substantially (often close to 2x). The change adds a hard 10-minute cap to each matrix leg at the same time it turns coverage on.

**Risk.** Coverage-instrumented unit tests can exceed 10 minutes and get killed. The failure reads as a timeout, not a coverage or test failure, which is hard to diagnose.

**Fix.** Set the timeout from a measured coverage-on run with margin, not a round guess. Or run coverage in a separate, longer-timeout job and keep the fast matrix uninstrumented.
